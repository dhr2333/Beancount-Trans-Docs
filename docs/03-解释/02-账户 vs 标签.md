# 账户 vs 标签

**账户搭骨架，标签加维度；选的时候只问一句：要进报表结构，还是只要事后能聚合？**

这句分工相对你要回答的问题与报表需求，不是永恒分类法。账本体系可以随认知收缩或改写；本文只固定「怎么判断」，不固定「哪一类事物永远该进账户或标签」。

## 账户适合什么

账户是**名词**（What）：描述「钱花在了哪一类事物上」。它是稳定的、客观的、基于交易本质的财务分类。

更适合放进账户的，通常是这些情况：

- **每笔必须有落点**：复式记账要求分录落到科目上，账户是借贷平衡的载体，每笔钱都要有一个答案。
- **类别长期稳定**：如交通、住房、饮食——在可预见的未来不会频繁改名的区分，适合做成账户路径。
- **互斥、不重不漏（MECE）**：每个账户代表一个相对独立的生活消费领域；一笔交易在结构上通常只落在一个叶子账户，总和才等于全部。
- **需要树状汇总**：账户天然有父子包含关系。想看「总饮食支出」，把各子账户相加即可。
- **保持粗粒度**：克制把账户拆到穷尽细节的欲望。某些账户注定是粗粒度或默认值，否则子账户会被无限细分，日常难以维护。

账户是用来记流水账的骨架，保证每笔钱有处可去，报表有稳定的结构可依。

## 标签适合什么

标签是**副词**（How / Why）：描述「这笔交易发生的背景、对象或目的」。它是灵活的、主观的、用于多维度交叉查询的元数据。

更适合用标签表达的，通常是这些情况：

- **语境、不必改结构**：项目、事件、归属、支出性质等——它们不改变「这笔钱在报表上算哪一类」，但改变你事后怎么筛它。
- **穿透账户树做筛选**：标签从 Food、Transport、Shopping 等不同账户里挑出同一侧面（如所有固定支出），用的是交集/并集，不是把子账户相加。
- **多维度、可叠加**：同一笔可以同时带上多个标签，每个标签是一个过滤条件；维度之间理想上彼此正交，尽量不重叠。
- **可选、可废弃**：标签不是入账必填项。认知变化后，可以合并、精简、归档——只保留你仍会反复追问的侧面。

如果一个维度用标签已经能稳定回答你的问题，就尽量不要为它再长一截账户路径，以免账户树膨胀。

## 同一笔里怎么用

同一笔交易，可以依次问两个问题：

- **这笔钱算哪一类？**（如饮食、交通）→ **账户**。每笔通常只落一个类别；选错会影响报表里的汇总结果。
- **除了类别，我还关心什么背景？**（如是否固定支出、是否家庭共用）→ **标签**。可以不打（一般默认为自己）；需要时也可以同时打多个。

两个问题分开答，不要硬塞进同一种工具。

**融合示例：** 宽带费记在 `Expenses:Culture:Subscription`，并打上 `#Fixed` 与 `#Family`。账户说明它属于订阅类支出；标签说明它是用于家庭的固定支出。两层各答一问，互不替代。

只按账户看，你能知道「订阅类花了多少」，但不容易分清：其中多少是刚性扣款、多少与家庭责任相关、多少完全在个人可控范围内。加上归属、性质等标签后，同一批流水可以从另一套问题被找回——例如「家庭相关的固定支出一共多少」。账户守住分类底线；标签拓展可问可查的上限。

## 收束

账户是交易的强制财务分类，构成互斥、可汇总的树状结构；标签是交易的可选语境元数据，构成可组合的分面，用于筛选与交叉分析。

维护上也可以反过来想：若某个标签频繁用于汇总、且需要独立余额，可以考虑升为账户，但需重新设计账户树以保持互斥完整。若某个账户不再用于报表、只用于筛选，可以降级为标签，让账户树保持简洁。体系会随认知变化——保留仍会追问的维度，废弃或归档不再需要的即可。
